The Crunch: From Always-On EC2 to Serverless Restaurant Agents

A practical migration story about turning a small restaurant concierge into a serverless AWS app, then extending it toward real reservation availability with Browser Use Cloud.

The Crunch AWS Lambda DynamoDB OpenRouter + DeepSeek Browser Use Cloud

The Crunch started as a charming restaurant planning app with a familiar early-stage deployment story: one always-on EC2 box, a Docker container, and a lot of implied operational responsibility hiding behind the phrase "it works."

That was fine for proving the idea. It was less fine for maintaining it. A restaurant concierge is bursty by nature. People open it when they are planning a night out, not because it needs a server burning money all afternoon. So the core question became simple: could we keep the product shape, preserve streaming chat, add real observability, and get rid of the always-on machine?

The answer was yes, but the path was not just "put it on Lambda." The useful part of the work was finding which parts belonged in the web runtime, which parts belonged in managed data stores, and which parts were better left as future worker jobs.

The Starting Point

The original architecture was direct: GitHub Actions SSHed into EC2, ran a Docker container, and the app served everything from a Bun server. That kept the stack understandable, but it left the app with the classic small-project tax:

Always-On Cost

An EC2 instance runs whether anyone is using the app or not.

Manual Runtime Ownership

The app owner inherits patching, host health, process supervision, and deployment drift.

Awkward Scaling

Traffic spikes and quiet periods are both handled by the same single box.

The product itself was more interesting than the infrastructure. The Crunch is a restaurant and bar concierge with a retro food-critic voice. It streams chat responses, uses tools for current restaurant research and geocoding, stores conversations, and supports both authenticated and trial flows. The challenge was to move the hosting model without flattening that experience.

Choosing The Serverless Shape

The first instinct was to stay AWS-native if possible. Cloudflare was attractive, especially for cost and simplicity, but moving to Cloudflare Workers would have meant adapting runtime assumptions, persistence choices, and server-side dependencies at the same time.

The AWS path that fit best was Lambda Web Adapter plus a container image. Bun could keep serving HTTP. GitHub Actions could keep building Docker. Lambda would handle scale-to-zero behavior. CloudFront would provide the stable public endpoint.

For chat persistence, DynamoDB became the right first serverless store. It fits the conversation access patterns, requires no VPC attachment, and keeps Lambda response streaming viable. Better Auth remained Postgres-backed through Supabase for now, which avoided mixing a compute migration with a full auth rewrite.

Part Decision Reason
Compute Lambda container with Lambda Web Adapter Preserved the Bun HTTP server while removing the always-on EC2 host.
Public Edge CloudFront in front of Lambda Function URL Gave the app a stable browser-facing endpoint and avoided direct Lambda URL cookie/origin confusion.
Chat Store DynamoDB Serverless, simple access pattern, no VPC requirement for streaming Lambda.
Auth Store Supabase Postgres for Better Auth Kept auth working while deferring the bigger auth-platform decision.
Secrets AWS Secrets Manager Kept runtime secrets out of tracked files and local bundles.
The key constraint: Lambda Function URLs support response streaming, but putting Lambda into a VPC to reach a private database would complicate that path. That made DynamoDB a better chat-store fit than Aurora Serverless for the first migration.

The Migration Work

Once the shape was clear, the work broke into a few practical tracks.

Track 1

Infrastructure. Add a CDK stack for ECR, Lambda, DynamoDB, Function URL, CloudFront, and permissions.

Track 2

Deployment. Update GitHub Actions to build, push, upsert runtime secrets, deploy CDK, invalidate CloudFront, and smoke test the app.

Track 3

Persistence. Move chat state behind a user-scoped database interface and use DynamoDB in production.

Track 4

Observability. Add Langfuse for LLM traces, Sentry scaffolding, and research eval reports.

Track 5

Product Surface. Add a trial chat flow with a 15-message cap so users can try the product before signing up.

A few bugs were especially clarifying. The app initially had origin issues because the browser was mixing local and deployed endpoints. The fix was to treat CloudFront as the canonical production URL and avoid using the raw Lambda Function URL for user flows.

Another bug was more embarrassing, and more useful: after switching the chat model to OpenRouter and DeepSeek, production briefly returned a Lambda runtime error blob as application/octet-stream. Chrome downloaded it like a file. The root cause was straightforward: local had OPENROUTER_API_KEY, GitHub Secrets did not. The deploy workflow had hardcoded the provider to OpenRouter, so Lambda crashed during startup.

The fix was not just adding the secret. The deploy smoke test now checks that the homepage returns Content-Type: text/html. That turns a subtle browser symptom into a direct CI failure.

Switching The Model Path

The Crunch originally used the Anthropic SDK directly. That worked, but model cost matters quickly once users start chatting and tools enter the loop. The app now supports a configurable provider path while preserving the existing Anthropic message and tool-use structure. 

LLM_PROVIDER=openrouter
LLM_MODEL=deepseek/deepseek-v4-pro
OPENROUTER_API_KEY=...

OpenRouter became the default route for DeepSeek V4 Pro, with direct DeepSeek and Anthropic fallback paths still available. This let the app keep its streaming loop, tool calls, and Langfuse/Sentry instrumentation without a full rewrite.

The lesson here was small but important: provider switches are easy locally and dangerous in CI if the secret story is not part of the change. A model migration is also a deployment migration.

The Browser Use Extension

Once the core app was serverless, the next product question became more ambitious: could The Crunch stop merely suggesting restaurants and actually check real reservation availability?

Restaurant booking is not just another API call. Resy and OpenTable are dynamic websites with bot defenses, date pickers, time selectors, account flows, and plenty of edge cases. Browser Use looked like a promising fit because it gives an AI agent a browser and a task, then lets it inspect and act on real pages.

The right first product goal is not "book it for me." It is "show me real availability and hand me the booking link."

Local Browser Use

The first probe used the open-source Python package locally with OpenRouter and DeepSeek. It worked on a smoke test and could drive basic browser actions. But on booking sites, the limits showed up quickly:

  • OpenTable allowed homepage interaction, then search requests returned 403 Access Denied.
  • Browser Use flagged the OpenTable flow as likely blocked by bot or captcha defenses.
  • Resy was more navigable, but the agent produced a likely false negative when search/autocomplete behavior was not handled carefully.

Browser Use Cloud

The docs made the missing piece clear: Browser Use's "undetectable" browser is the Cloud product, not the plain local Chromium path. Cloud v3 provides managed stealth browsers, residential proxies, captcha handling, recordings, live preview, and structured output.

With Browser Use Cloud, the same OpenTable experiment improved immediately. The agent got past the earlier 403, found the L'Artusi OpenTable page, and discovered that OpenTable does not book L'Artusi directly. Then the Resy probe found the actual reservation page and returned visible availability.

Probe Result What It Means
Local OpenTable Blocked by 403 Access Denied Normal local browser automation is not enough for this class of site.
Cloud OpenTable Reached L'Artusi page, found "not available on OpenTable" Stealth browser path produced useful evidence instead of a network blocker.

The Architecture That Wants To Exist

The Browser Use experiment should not be shoved into the Lambda web server. Browser automation is slower, more failure-prone, and more resource-intensive than a normal chat request. It wants to be a worker.

Availability Result

The production version should probably look like this:

  1. The user asks for a real reservation check.
  2. The app gathers restaurant, date, time, party size, and platform.
  3. The app queues a job with strict domain and action guardrails.
  4. A worker calls Browser Use Cloud and stores the result, recording link, and booking URL.
  5. The chat returns availability evidence and asks the user to complete the booking manually.

That design keeps the main chat experience responsive and keeps booking actions human-confirmed. It also gives us auditability: which site was checked, what slots were visible, what the browser saw, and where the user should go next.

What Changed In The Repo

The work landed across a few branches and commits. The useful end state is less about individual commits and more about the new capabilities.

  • Serverless deploy path: GitHub Actions, ECR, CDK, Lambda Web Adapter, Function URL, CloudFront.
  • Production chat persistence: DynamoDB with user-scoped conversations.
  • Auth persistence: Better Auth tables in Supabase Postgres.
  • Trial flow: /try/new and trial chat APIs with a 15-message cap.
  • LLM provider path: OpenRouter plus DeepSeek V4 Pro, with fallbacks.
  • Monitoring: Langfuse tracing, Sentry scaffolding, and research eval reports.
  • Browser Use spike: local and Cloud reservation probe scripts plus findings documentation.

Lessons

Serverless Is A Product Decision

It is not just cheaper hosting. It changes what you monitor, test, and isolate.

Secrets Are Part Of The Feature

A local provider switch is incomplete until CI and runtime secrets are proven.

Agents Need Boundaries

Reservation agents should check and explain, not silently book.

The Crunch is now much closer to the kind of app it wants to be: small, maintainable, serverless by default, and capable of using specialized workers for the messy parts of the web.

The most interesting part is that the future feature is not a generic "browser agent." It is a restaurant-specific availability agent with a narrow job, strict guardrails, evidence capture, and a graceful handoff to the user. That is where browser automation starts to feel like product infrastructure rather than a stunt.
